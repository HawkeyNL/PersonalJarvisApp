# Desktop release setup — owner actions only

Repository: `HawkeyNL/PersonalJarvisApp` (public). No third artifact repository,
Home Node address, inbound SSH, or GitHub write token on the Home Node is used.
These instructions do not authorize or perform a release themselves.

## GitHub configuration

Create the environment `application-release`. Where the GitHub plan supports
it, require owner approval and restrict deployments to `main`.
Ordinary `ci.yml` has read-only contents permission and no release secrets.
Only the final release job requests `contents: write` using its own repository's
`GITHUB_TOKEN`; repository/organization Actions policy must permit that scope.
Do not give the workflow a personal access token or bypass protected reviews.

Set the repository variable `TAURI_SIGNING_PUBLIC_KEY` to the public key text
generated by Tauri. It is not secret. Set these environment secrets:

- `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
- `MACOS_DEVELOPER_ID_CERTIFICATE_P12_BASE64`
- `MACOS_DEVELOPER_ID_CERTIFICATE_PASSWORD`
- `MACOS_DEVELOPER_ID_APPLICATION`
- `MACOS_NOTARY_API_ISSUER_ID`
- `MACOS_NOTARY_API_KEY_ID`
- `MACOS_NOTARY_API_PRIVATE_KEY_BASE64`

macOS is a required production target: absent signing/notary credentials must
fail the workflow, not produce an unsigned substitute. Windows has Tauri update
signatures but currently **no Authenticode signing**. Do not describe its installer
as Authenticode-signed. No Windows signing certificate is required by this workflow.

For `main`, recommend PR reviews, required desktop frontend/native CI checks,
no force pushes, and no branch deletion. Optionally dismiss stale reviews.
Choose and document the owner's admin-bypass policy explicitly; availability of
review features depends on the GitHub plan, so they are not assumed configured.

## Generate and protect the updater key

Use the lockfile's Tauri 2 tooling. The command below was checked against its
`signer generate --help`; it prompts for the private-key password. Never use
the password command-line option, print a private key, or create keys in this
repository. Do not run this if an existing deployed signing key must be retained.

```bash
npm ci
install -d -m 0700 "$HOME/.local/share/jarvis-signing"
umask 077
npm run tauri -- signer generate \
  --write-keys "$HOME/.local/share/jarvis-signing/desktop.key"
```

Keep `desktop.key` and its password in secure owner backups. Upload the private
key through GitHub's secret UI, never through a committed file or shell command
containing its contents. The `.pub` file supplies `TAURI_SIGNING_PUBLIC_KEY` and
the Home Node mirror's pinned public key. Release builds embed only that public
key via `JARVIS_TAURI_UPDATER_PUBKEY`. Losing the private key interrupts update
continuity. Rotation requires an explicit migration for already installed clients;
changing a repository variable alone does not update their trust anchors.

The Home Node verifies the signed `latest.json`, hashes/sizes, and each Tauri
signature before promotion. Clients independently verify the updater signature.
A compromised mirror or public asset downloader cannot sign a future update.

## First release: app-v0.1.0

1. Merge both reviewed migration PRs manually, with CI passing. Do not merge
   automatically or rewrite Core history.
2. Configure the environment, variable and secrets above; securely back up keys.
3. Confirm npm `package.json`, both version entries in `package-lock.json`,
   `src-tauri/Cargo.toml`, and `src-tauri/tauri.conf.json` all say `0.1.0`.
4. Run `python3 update-release/desktop_release.py --version 0.1.0` and full CI.
5. Dispatch `.github/workflows/release.yml` on `main`, input version `0.1.0`.
6. Approve `application-release` jobs where approval is configured.
7. Inspect platform checks: Linux x86_64 AppImage; Windows x86_64 NSIS;
   macOS arm64 Developer ID, hardened runtime, notarization and stapling.
8. The final job verifies the complete same-SHA artifact set, signs the manifest,
   creates a draft, uploads, redownloads and verifies it before publishing.
   A failed job must leave the draft unpublished; diagnose it before another attempt.
9. Verify the successful `app-v0.1.0` release, `latest.json`, its signature and
   all platform assets. Do not manually publish a partially failed draft.
10. Follow Core's `docs/app-updates/PRIVATE_RELEASES.md` for installing the
    server-owned sync service, public-source configuration and one manual sync
    before enabling its timer. No GitHub token is required for the public source.
11. Configure Core's mirror root and runtime HTTPS public origin, restart Core,
    and check readiness and capability through an enrolled native client.
12. Install/pair each platform client. End-to-end update installation requires
    a subsequent signed compatible version; a first release alone cannot prove it.

The workflow has no production Home Node connectivity or deployment step.
Signing secrets, real Windows/macOS runners and a published release are required
for production acceptance; local mock tests do not substitute for those checks.

## Updating the shared protocol dependency

The authoritative crate is `PersonalJarvis/crates/client-core`. Merge/review its
compatible change there first, obtain the exact 40-character commit SHA, update
the `rev` in this repository's `src-tauri/Cargo.toml`, and refresh Cargo.lock.
Never use a floating branch, local sibling path, or a copied crate. Run frontend,
native and protocol tests and review the lock diff before releasing the app.
Core releases do not automatically bump this pin or release the desktop app.
